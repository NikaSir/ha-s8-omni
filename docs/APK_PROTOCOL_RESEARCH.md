# S8 OMNI: исследование APK, Tuya-панели и бинарных команд

Дата фиксации: **2026-09-04**

## 1. Результат этапа

Исследование изменило исходную постановку задачи.

Штатное Android-приложение Smart Life не является единственным местом, где
реализована логика S8 OMNI. Для лазерных роботов Tuya использует загружаемую
панель-миниприложение. Базовый APK содержит контейнер и SDK, а устройство-
специфичная панель получает схему DP по коду и использует отдельные пакеты
`@ray-js/robot-map`, `@ray-js/robot-data-stream` и
`@ray-js/robot-protocol`.

Следовательно, статическая распаковка одного APK полезна для изучения
транспорта и API, но **не гарантирует наличие актуальной логики панели именно
S8 OMNI**. Для достоверного результата требуются три слоя:

1. фактическая схема DP конкретного экземпляра S8 OMNI;
2. загруженная панель/миниприложение либо запись её DP-переходов;
3. физическое подтверждение команды на реальном устройстве.

В этом репозитории добавлен автономный инструмент
`scripts/tuya_robot_protocol.py`. Он:

- разбирает стандартные кадры Tuya RobotProtocol `AA` и `AB`;
- проверяет заявленную длину и checksum;
- декодирует основные команды комнат, зон, точки и редактирования карты;
- извлекает такие кадры из текстовых/JSON-диагностик;
- сканирует экспорт схемы и ищет DP по точному `code`;
- не подключается к устройству и не умеет записывать DP.

Производственный код интеграции и текущие команды S8 OMNI на этом этапе не
изменялись.

## 2. Уровни достоверности

| Уровень | Что относится | Разрешённое применение |
|---|---|---|
| **S8_VERIFIED** | DP и переходы, подтверждённые диагностикой и физическим поведением нашего S8 OMNI | Использование в интеграции после теста и readback |
| **TUYA_STANDARD** | Форматы из открытого `Tuya-Community/tuya-ray-materials`, `RobotProtocol` и `SweepRobotTemplate` | Декодирование, построение гипотез, подготовка теста |
| **FAMILY_REFERENCE** | Схемы других Tuya-роботов с похожим набором DP | Только поиск кандидатов; перенос номера DP запрещён |
| **UNKNOWN** | Назначение неподтверждённого DP, версия карты, версия payload, транспорт конкретной команды S8 | Никаких записей |

Ключевое правило:

> Назначение определяется точным строковым `code` в фактической S8-схеме.
> Одинаковый номер DP у другой модели не является доказательством.

### 3.2. Подтверждённые последовательности

- Новый старт уборки: один атомарный Tuya LAN-запрос
  `mode=smart`, `pause=false`, `power_go=true`.
- Продолжение после паузы: только `pause=false`.
- Пауза: `power_go=false`, затем `pause=true`.
- Возврат во время уборки:
  `power_go=false` → `pause=true` → дождаться `standby|paused` →
  `mode=chargego` → дождаться фактического состояния возврата/зарядки.
- Операции станции: DP134/135/136, `true` — старт, `false` — стоп;
  старт разрешён только при подтверждённой парковке.

Эти переходы относятся к простым DP и не доказывают наличие либо номер
бинарного DP `command_trans`.

## 4. Что найдено в открытом исходном коде Tuya

Исходная база:

- `Tuya-Community/tuya-ray-materials`;
- модуль `utils/RobotProtocol`;
- шаблон `template/SweepRobotTemplate`;
- исследованный снимок репозитория: commit
  `83e20f5fe193a48245f521ff7119a53bafa989d1`.

### 4.1. Формат кадра

Стандартный формат с версией 1:

```text
AA 01 LLLLLLLL CMD DATA CHECKSUM
```

Стандартный формат с версией 0:

```text
AA 00 LL CMD DATA CHECKSUM
```

Расширенный формат:

```text
AB 00 LLLLLLLL CMD DATA CHECKSUM
```

Где:

- `LL`/`LLLLLLLL` — число байтов `CMD + DATA`;
- `CHECKSUM = sum(CMD + DATA) mod 256`;
- многобайтовая длина записана в big-endian;
- `CMD` — один байт команды.

Официальный декодер Tuya проверяет команду и длину payload. Наш автономный
декодер дополнительно проверяет checksum и отсутствие лишних байтов.

### 4.3. Уборка выбранных комнат

#### V1 — команда `0x14`

```text
DATA = CLEAN_TIMES ROOM_COUNT ROOM_ID...
```

Официальный контрольный пример:

```text
AA 01 00000006 14 01 03 04 05 03 24
```

Расшифровка:

- один проход;
- три комнаты;
- ID комнат `4, 5, 3`;
- checksum `0x24`.

#### V2 — команда `0x56`

```text
DATA =
  ROOM_COUNT
  [ROOM_ID SUCTION CISTERN Y_MOP CLEAN_TIMES]...
```

Вариант v2 способен передать отдельный профиль для каждой комнаты.

### 4.4. Профиль комнаты

`0x22/0x23`:

```text
ROOM_COUNT
[ROOM_ID SUCTION CISTERN Y_MOP CLEAN_TIMES]...
```

`0x58/0x59`:

```text
ROOM_COUNT
[ROOM_ID CLEAN_MODE SUCTION CISTERN Y_MOP CLEAN_TIMES]...
```

Справочные enum из открытого Tuya-модуля:

| Поле | Значения |
|---|---|
| `CLEAN_MODE` | `0 both_work`, `1 only_sweep`, `2 only_mop`, `3 mop_after_sweep` |
| `SUCTION` | `0 closed`, `1 gentle`, `2 normal`, `3 strong`, `4 max` |
| `CISTERN` | `0 closed`, `1 low`, `2 middle`, `3 high` |
| `Y_MOP` | `0 off`, `1 on`, `3 high` |

Значения S8 должны быть проверены фактической схемой/трассой. Например,
текущая простая DP9-схема S8 подтверждала только
`gentle/normal/strong`; наличие `max` внутри бинарного room payload пока не
доказано.

### 4.5. Зональная и точечная уборка

`0x28/0x29` v1:

```text
CLEAN_TIMES ZONE_COUNT
[POINT_COUNT X16 Y16 ...]...
```

`0x3A/0x3B` v2 имеет внутреннюю версию payload:

- protocol 1 — зоны и имена;
- protocol 2 — добавлены общий режим, всасывание, вода и число проходов;
- protocol 3 — сохранённые зоны, ID, порядок и индивидуальные параметры.

`0x3E/0x3F` v2:

- protocol 1:
  `MODE SUCTION CISTERN CLEAN_TIMES X16 Y16`;
- protocol 2:
  `POINT_COUNT [X16 Y16]...`.

Координаты являются смещениями относительно origin карты и требуют
`mapScale`. Применять их как абсолютные координаты без заголовка фактической
карты нельзя.

### 4.6. Редактирование карты

- `0x1C`: `ROOM_ID + две точки линии разделения`;
- `0x1E`: список объединяемых `ROOM_ID`;
- `0x24`: для каждой комнаты `ROOM_ID + длина UTF-8 + поле имени 19 байт`;
- `0x26`: `ROOM_COUNT + ROOM_ID...`;
- `0x38`: запретные области, режим запрета, геометрия и имя;
- `0x48`: виртуальные стены с отдельным режимом;
- `0x52`: материал пола комнаты.

## 5. Последовательность отправки в официальном SweepRobotTemplate

Открытый шаблон Tuya привязывается не к номеру DP, а к строковому коду:

```text
command_trans
mode
switch_go
```

Для выбранных комнат, зоны и точки шаблон делает:

```text
1. сформировать RobotProtocol frame;
2. записать frame в DP, чей code == command_trans;
3. записать соответствующий mode;
4. записать switch_go = true.
```

В исходном коде отдельно отмечено, что такие DP-записи не объединяются:
прошивка ожидает порядок **commands → mode → switch/pause**.

Это отличается от подтверждённого нового старта S8, где три простых DP
отправляются атомарно. Конфликта нет: речь идёт о разных сценариях. Для
комнат/зон сначала требуется доставить бинарный payload.

## 6. Почему DP145 остаётся заблокированным

Схемы других Tuya-роботов показывают, что один и тот же номер может иметь
разные коды:

- у одной модели DP145 — `manual_status`;
- у другой — `pending_save_map`;
- `command_trans` встречается, например, как DP15 либо DP199.

Это доказывает только одно: перенос numeric DP между моделями недопустим.

Для S8 OMNI разрешение записи появится только после факта вида:

```json
{
  "abilityId": "<конкретный DP>",
  "code": "command_trans",
  "type": "Raw"
}
```

До этого:

- DP145 не записывается;
- никакой другой Raw DP не объявляется командным;
- пробные кадры не отправляются.

## 7. Автономный инструмент

### 7.1. Декодировать один кадр

```bash
python scripts/tuya_robot_protocol.py frame \
  aa010000000614010304050324
```

### 7.2. Построить кадр стандарта офлайн

```bash
python scripts/tuya_robot_protocol.py encode 0x14 \
  --data 0103040503
```

Команда только возвращает байты. Она не имеет сетевого транспорта и не
записывает устройство.

### 7.3. Проверить экспорт схемы

```bash
python scripts/tuya_robot_protocol.py schema \
  /path/to/sanitized-device-schema.json
```

Ожидаемый решающий результат:

```json
{
  "command_transport_confirmed": true,
  "command_transport_candidates": [
    {
      "code": "command_trans",
      "dp_id": 15,
      "type": "Raw"
    }
  ]
}
```

Число `15` здесь только пример формата вывода, не утверждение о S8.

### 7.4. Найти кадры в диагностике

```bash
python scripts/tuya_robot_protocol.py extract \
  /path/to/sanitized-trace.json \
  --strict
```

## 8. Следующий обязательный захват

Для перехода от Tuya-стандарта к S8_VERIFIED нужны следующие данные.

### Шаг A — схема

Получить санитизированный список DP S8 с полями:

- numeric id / `abilityId`;
- exact `code`;
- type;
- access mode;
- range/maxlen.

Не нужны и должны быть удалены:

- Device ID;
- Local Key;
- IP;
- SID/token;
- UUID и идентификаторы аккаунта.

### Шаг B — пассивная трасса штатной панели

На каждом тесте фиксировать полный снимок DP до и после команды и отдельно
все изменившиеся Raw/String DP:

1. выбрать одну комнату и запустить;
2. выбрать две комнаты и запустить;
3. поставить одну прямоугольную зону;
4. выполнить «Куда убрать»/точечную уборку;
5. изменить порядок комнат;
6. изменить профиль одной комнаты;
7. переименовать тестовую комнату.

Для первой итерации достаточно пунктов 1–4.

### Шаг C — доказательство

Команда считается подтверждённой для S8, только если одновременно выполнено:

1. найден exact DP code `command_trans`;
2. кадр проходит длину и checksum;
3. command byte соответствует действию штатной панели;
4. последовательность DP воспроизводится локально;
5. устройство физически выполняет ожидаемое действие;
6. статус/readback подтверждает результат;
7. команда безопасно прекращается штатной Pause/Home.

## 9. Что пока не переносится в интеграцию

До S8-захвата не добавляются:

- уборка комнат;
- зональная уборка;
- «Куда убрать»;
- редактирование карты;
- виртуальные стены и запретные области;
- локальные таймеры RobotProtocol;
- DND schedule через бинарный payload;
- сохранение/удаление/выбор карты;
- сброс расходников;
- запись в DP145.

Текущие подтверждённые Start/Pause/Home и операции станции остаются без
изменений.
